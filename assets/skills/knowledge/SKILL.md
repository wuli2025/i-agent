# 知识体系构建：可 grep 的文件式知识库

目标：把任意规模的资料整理成短上下文模型也能可靠使用的知识库。核心原则：**知识存在文件里而不是上下文里；用 grep 精确定位，只把命中的最小片段读进上下文。** 这样 8k 上下文也能驾驭百万字资料。

## 一、知识库即文件夹

```
kb/
  overview.md      # 总纲 + 文件索引（知识库的入口和地图）
  entities/        # 每个实体一个文件
    张三.md
    某某公司.md
  terms.md         # 术语表
  relations.md     # 关系三元组表
  errata.md        # 勘误记录
```

- **overview.md**：开头 10 行内写清知识库主题、覆盖范围、更新日期；其后是文件索引——entities/ 下每个文件一行（文件名 + 一句话简介）。任何任务开始先读 overview.md，它必须小到一次读完。
- **entities/ 每实体一文件**，文件名即实体规范名。frontmatter 固定三字段：

```
---
name: 实体规范名
type: 人物/组织/事件/概念/产品/地点
aliases: 别名1, 别名2, 简称, 英文名
---
```

正文自由分节（简介/关键事实/时间线/出处），每条事实尽量带出处。

- **terms.md**：术语表，一行一条，格式 `术语 | 定义（一行说完）`。定义超一行的，升级为 entities/ 实体文件，术语表留一行指向它。
- **relations.md**：关系三元组表，格式 `主体 | 关系 | 客体 | 出处`，一行一条。如 `张三 | 创立 | 某某公司 | 资料A第3章`。这是回答"谁和谁什么关系""某公司有哪些产品"类问题的主索引。
- **errata.md**：勘误表，见第五节。

## 二、grep 检索策略（使用知识库的唯一正确姿势）

- **查实体**：先 `grep -l "关键词" kb/entities/` 匹配 aliases 和正文；aliases 字段的存在就是为了让"腾讯/Tencent/鹅厂"都能命中同一文件。命中后再 read 该文件全文。
- **查关系**：grep relations.md 中的实体名，命中行即三元组本身，多数情况不必再读别的文件；需要细节再顺着"主体/客体"去读实体文件。
- **查术语**：grep terms.md，命中行即答案。
- **写作或回答前必检索**：凡是要陈述知识库覆盖范围内的事实，必须先 grep 再落笔，禁止凭上下文残留印象作答。grep 无命中就明说"知识库未收录"。
- 红线：**绝不 cat 整个 kb/ 进上下文**。overview.md 是唯一允许整读的导航文件。

## 三、入库流程（增量合并，不重复建卡）

新资料入库四步：

1. **抽取**：从资料中抽实体、术语、关系三元组，各成清单。
2. **查重**：对每个待入库实体，先 grep entities/ 的 name 和 aliases。**已存在则在原文件追加新事实、补充新别名，绝不新建重复文件**；不存在才建新文件。术语、关系同理先 grep 再插入。
3. **合并**：新事实追加到实体文件对应小节，注明出处；新三元组追加到 relations.md；发现与旧内容矛盾的走勘误规约（第五节），不要静默覆盖。
4. **更新索引**：新建的实体文件必须在 overview.md 文件索引区加一行。索引与实际文件不一致是知识库最常见的腐坏方式，每次入库收尾必须核对。

## 四、大资料集处理（分片扇出）

资料超过单次可读规模（约 5000 字以上）时：

- 先用 shell 切分或按天然章节划片，每片一个 task 子任务做抽取，子任务只拿自己那一片 + 抽取格式说明，产出写到临时文件（如 `kb/_inbox/片名.md`，格式与正式表一致）。
- **主任务只做合并去重**：逐片读 _inbox 产物，按第三节流程 grep 查重后合入正式文件，然后删除临时片。主任务上下文里只有"当前正在合并的这一片"，永远不持有全部资料。
- 子任务之间无依赖，可并行。

## 五、勘误规约

发现新旧资料矛盾时：

- 记入 errata.md，一行一条：`旧说法 | 新说法 | 依据 | 日期`。
- **不直接删改旧文件里的原内容**，而是在原处追加标注 `（存疑，见 errata.md YYYY-MM-DD 条）`，让矛盾可追溯。
- 确认新说法成立后，实体文件正文以新说法为准陈述，旧说法保留在勘误表中。
- 回答涉及勘误条目的问题时，grep errata.md 确认当前有效说法。
